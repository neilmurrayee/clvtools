## Blockers

### 1. The installed package cannot find its data

`src/clvtools/data.py:47` · `dist/clvtools-0.1.0-py3-none-any.whl`

**Evidence.** `DATA_DIR` resolves three directories above the module, to a
`data/` folder that exists only in a checkout. Listing the wheel shows 26
Python files, `py.typed`, the licence, and zero CSVs. After `pip install`,
`load_apparel_trans()` is a `FileNotFoundError`, so the README's Usage block
fails on its first statement. Backlog item 15 is about uploading exactly this
wheel.

**Fix.** Move the five CSVs under `src/clvtools/data/` and resolve them with
`importlib.resources`. Add a test that builds the wheel, or inspects the sdist
file list, and asserts the CSVs are present. Correct "four datasets" to five in
the README, `pyproject.toml` and backlog item 5 while there.

### 2. CI has never been green, and the records say it has

`docs/backlog.md` item 17 · commit `faea7f6` · GitHub run 33599631277

**Evidence.** Three CI runs exist. The first died resolving an action, the
second failed 9 tests on both interpreters, and the third, for the commit that
claims to fix it, failed 7 on both. The failures are: the Gamma-Gamma paper
check rounds `gamma` to 56.505 on Linux against the paper's 56.504 (the true
value is 56.5045, a rounding boundary); the Nelder-Mead regression guard
asserts SciPy's default *reports success* at a bad optimum, but on Linux it
exhausts its evaluation budget instead; the evaluation-count gate wants 200 to
400 and Linux does it in 185; and four doctests print Pareto/NBD digits the
ridge does not fix. The Linux fit's log-likelihood is `-5848.097826902405`
against `-5848.09782690329` here. The optimiser is not worse on Linux. The
assertions are asking for digits neither platform determines.

**Fix.** Reopen item 17 with the run URL and a rule for ticking it: paste the
run id. Adopt one precision rule for every quantity a fit produces: assert
against the paper with a tolerance derived from the ridge (about 1e-3 absolute
on these parameters), assert the log-likelihood tightly, and never assert a
printed digit of an estimate. The in-flight edits in the working tree follow
that shape and should land. Then consider whether to end every L-BFGS-B fit
with a short Nelder-Mead polish so the *reported* point is stable across
libms, which would let the doctests print more digits honestly. Either is
defensible. Choosing neither is what produced three red runs.

## Defects: wrong or silently degraded numbers

Every item here was reproduced against the bundled data unless marked
otherwise. None is a wrong equation. Each is an input, a regime, or a failure
mode the oracle fixtures do not visit.

### 4. GGom/NBD loses its death term for heavy buyers

`src/clvtools/ggomnbd.py:133-147` (likelihood integrand) · `241-254` (CET)

**Evidence.** The integrands are formed in the direct domain with
`(alpha + tau)^(r + x)` and no scale factored out. At the fitted parameters
with `T = 104`:

```
x = 100   CET 29.44   PAlive 0.9277   LL -139.07
x = 140   CET  0.00   PAlive 0.8551   LL -148.47
x = 160   CET   nan   PAlive 1.0000   LL -148.85
```

PAlive is exactly 1.0 because the integral underflows to zero, its log is
`-inf`, and `logaddexp` returns the alive branch alone. On daily data with `T`
near 1000 this starts around `x = 105`. The Pareto/NBD handles the same regime
correctly.

**Fix.** Evaluate the log integrand at the lower limit once, integrate
`exp(log f(y) - log f(t_x))`, add the offset back, and rewrite the CET's
`lower` factor in log space. Pin it with a fixture column at `x = 200`: the
oracle's own arithmetic may fail there too, in which case the cross-check is
the Pareto/NBD limit the README already documents.

### 5. Validation is looser than the likelihood

`src/clvtools/pnbd/fit.py:117` · `bgnbd.py:412` · `ggomnbd.py:432` · `pnbd/aggregate.py:190-217`

**Evidence.** The fits accept `t_x <= T + 1e-9`. The likelihood needs
`t_x <= T` exactly: a ratio above one makes an intermediate negative and its
log NaN. One customer at `t_x = T + 1e-10`, which floating-point date
arithmetic can produce, makes every objective evaluation infinite, and the fit
returns `r = alpha = s = beta = 1.0`, log-likelihood `-inf`,
`converged = False`, and raises nothing.

**Fix.** After validation, `t_x = np.minimum(t_x, T)`. Then make a non-finite
objective at the start point an exception rather than a returned object.

### 6. NaN in the inputs becomes a plausible output

`src/clvtools/data.py:366-370` (prices) · `data.py:706` (covariates) · `_staticcov.py:405-436`

**Evidence.** Covariates are cast with `astype(float)` and never checked. One
NaN in `Gender` returns a static-covariate "fit" at the start values with
`log_likelihood = -inf`, hundreds of RuntimeWarnings, and no exception.
Separately, a customer whose prices are all NaN is counted in `x` but dropped
from the mean, and `fillna(0.0)` then records `Spending = 0.0`. The
Gamma-Gamma fit silently drops that row, and `predict()` reports mean spending
7.72 for that customer against 88.65 with real prices. The same filter,
`gg.py:559`, silently excludes any customer with purchases but zero total
spend, which real logs full of refunds and vouchers will contain.

**Fix.** Reject non-finite `Price` in `ClvData.__init__` and non-finite
design matrices in `ClvDataStaticCov`. Warn, with a count, when the
Gamma-Gamma drops customers.

### 7. Non-convergence is silent in every family

`pnbd/fit.py:254` · `gg.py:361` · `bgnbd.py:444` · `ggomnbd.py:464` · `correlation.py:352` · `_staticcov.py:436`

**Evidence.** There is no `warnings.warn` anywhere in `src/`. Every fit sets
`converged = bool(result.success)` and returns. `fit_pnbd(..., maxiter=2)`
returns `[0.384, 1.682, 0.309, 1.335]` with no signal beyond the flag.
CLVTools warns. For the covariate fits the flag is also ambiguous:
`_staticcov.py:247-277` reports whichever of L-BFGS-B or the Nelder-Mead
polish scored lower, so a failed gradient search followed by a successful
polish reads as converged, and a polish that improves the objective but hits
its 20,000-evaluation cap reads as failed. (The flag semantics are from code
reading; both stages converged in the fits instrumented.)

**Fix.** One shared helper that packages the optimiser result, warns on
`not success` with the message and the family name, and raises on a
non-finite objective. Use it from all six fits. Report both stages' outcomes
for the covariate search.

### 8. Standard errors cannot be obtained on three estimators

`src/clvtools/estimate.py:147-149` · `pnbd/correlation.py:262-272` · `ggomnbd.py:574-584` · `pnbd/dyncov.py`

**Evidence.** The `latent_attrition` docstring lists `hessian` among the
forwarded keywords. `fit_pnbd_correlated` has no such parameter, so
`latent_attrition(pnbd, data, use_cor=True, hessian=False)` is a `TypeError`;
without it the correlated fit's Hessian is always `None` and `summary()`
raises with the advice "fit with hessian=True", which cannot be followed.
`fit_ggomnbd_staticcov` hard-codes `hessian=False` and rejects the keyword the
same way. The dyncov fit has neither the argument nor the field. Also, the
correlation parameter `m` is excluded from z- and p-values at
`inference.py:265`, where CLVTools prints one for it.

**Fix.** Add `hessian` to the three fits; for the GGom it is a
`SearchSettings` plumbing change. Add `m` to the names that receive z-values.

### 9. NaN standard errors ship as a converged fit

`src/clvtools/inference.py:344, 362` · `_staticcov.py:397-425`

**Evidence.** The BG/NBD covariate fit on the apparel data lands at
`a = 5.2e5, b = 3.8e6`, the ridge the README documents. There the Hessian is
not positive definite: `life.Gender` gets SE `nan` beside `life.Channel` at
0.594, and `converged` is `True`. `_covariance` inverts and takes `sqrt(diag)`
without checking. Related and unconfirmed against R: for regularized fits the
Hessian is differenced on the unpenalised *sum* while the objective minimised
is the penalised *mean*, so the standard errors refer to a different function
than the estimates. No fixture covers a regularized `vcov`; every regularized
test passes `hessian=False`.

**Fix.** Check `eigvalsh(hessian) > 0` in `_covariance` and warn naming the
flat directions. Decide which objective regularized standard errors refer to,
document it, and add one oracle fixture for a regularized fit's `vcov`.

### 10. The dyncov death term underflows where the oracle does the same

`src/clvtools/pnbd/dyncov.py:283, 322` · `dyncov_predict.py:284-286`

**Evidence.** The F2 terms are formed as `value / alpha**a` with
`a = r + s + x`. At `alpha` near 200 the term is 1.3e-124 at `x = 50`,
1.2e-285 at `x = 120`, and exactly 0.0 at `x = 160`. The failure mask watches
the hypergeometric value, not the divided term, so the customer likelihood
takes the alive-only branch at lines 599-600 with no signal. This mirrors
CLVTools' arrangement, so agreement with fixtures proves nothing here. The
dyncov CET also divides by `s - 1` unguarded where the aggregate module raises
near `s = 1`. Related, at extremes only: the Pareto/NBD `pmf` at
`aggregate.py:529, 539` calls `hyp2f1` with no fallback and returns NaN for
`k >= 23` at `alpha = 500, beta = 1`.

**Fix.** Keep `log(term) = log(value) - a * log(alpha)` and combine the two F2
terms with a signed log-sum-exp. Add the `s` near 1 guard. Guard the pmf call
with `isfinite` and fall back to the series.

### 11. Bootstrap is brittle and slow in the wrong place

`src/clvtools/bootstrap.py:69-79, 171-181`

**Evidence.** No error handling around the refit loop: an exception on draw 3
of 5 propagates and nothing is returned. Refits with `converged = False` are
pooled into intervals with no warning. A user-supplied `sample` never receives
the seeded generator, so `seed` is silently ignored with it. And
`bootstrap_data` filters the whole frame once per drawn customer: 0.95 s per
draw on CDNOW against 0.16 s for the summary and Pareto/NBD fit together, so a
hundred draws spend about 95 s rebuilding data.

**Fix.** Collect failures and report how many draws converged, pass the
generator to `sample`, and build resamples from `groupby("Id").indices` once.

### 12. Seven smaller silent paths

`src/clvtools/data.py` · `predict.py` · `README.md:52`

- **Duplicate covariate rows** (`data.py:690`) give a 601-row design matrix
  and die with a broadcast error deep in the likelihood instead of naming the
  id.
- **Timezone-aware dates** raise a tz-compare `TypeError` with a date split or
  the year unit (`data.py:262`, `timeunit.py:124`); with a numeric split they
  build and `t_x` drifts by up to an hour across a DST change
  (`timeunit.py:94`).
- **`predict(newcustomer(52), pnbd, gg)`** ignores `gg` and `prediction_end`
  without saying so (`predict.py:590`).
- **A `name_price` typo** silently disables spending (`data.py:193`) where an
  id or date typo raises.
- **The README Usage snippet** discounts DERT and CLV at the unscaled annual
  rate. On weekly data total DERT is 92.92 against 2642.78 with
  `discount_factor(0.10)`. The docstring warns; the README does not.
- **`likelihood_ratio_test`** accepts two non-nested models and reports a
  chi-square.
- **`ClvDataDynCov`** validates nothing at construction (`data.py:824-840`);
  errors surface at `walks()`.

**Fix.** Each is a few lines: uniqueness check after `set_index`, normalise or
reject tz-aware timestamps in `ClvData.__init__`, raise when unused arguments
are passed with a new-customer spec, raise on an explicit missing price
column, and fix the README snippet.

### 16. The fixture directory has drifted from its generators

### 17. Markers, clocks and coverage say slightly more than they mean

### 19. The three families have diverged around the shared machinery

`pnbd/fit.py:107-120` · `bgnbd.py:405-413` · `ggomnbd.py:425-433` · `correlation.py:313` · `_staticcov.py:350-354` · `pnbd/staticcov.py:628-655`

transpose.

**Fix.** One shared validator called from all six fits; one result shape;
`type(self).__name__` in the repr; a docstring line about `cbs["T"]`.

## What is working

This is worth stating because the fixes above should not disturb it. The
oracle discipline is real: per-customer fixtures at several parameter vectors,
aligned by id, with independent cross-checks (numerical marginalisation
against closed forms, nesting at zero covariates and `m = 0`). The core
Pareto/NBD path is numerically careful throughout: log space, `logaddexp`, the
`t_x = T` branch explicit, and a real fallback for the one hypergeometric
corner SciPy misses. SciPy's `hyp2f1` was checked against an exact series to
1e-12 across the regime the models use. Static analysis and typing are gates,
not advice. The documentation is dense, cross-referenced, and its counts hold
up: every test, fixture and coverage number quoted across five files was
verified to match. Nothing in this review suggests a wrong equation.
